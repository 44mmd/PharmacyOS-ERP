# PharmacyOS ERP — Arabic-first localization

Arabic is a first-class language of PharmacyOS ERP, and English stays fully available. Everything below
lives in the `pharmacyos_erp` app. No Frappe or ERPNext translation file is edited
(`pharmacyos/FORK_PATCHES.md`).

## Language & locale defaults

* **Iraqi deployments default to Arabic.** `setup/install.py:configure_locale` runs on install and in the
  `patches/v1/arabic_first_locale` patch. When *System Settings → Country* is **Iraq**, it sets:
  * System language `ar` (RTL);
  * time zone `Asia/Baghdad`;
  * IQD stays the currency (`configure_currency`).

  Sites in other countries, including upstream test sites, are not touched.
* **Per user:** *My Settings → Language*. The choice survives logout/login. In validation, a user was switched
  to Arabic, logged out and back in, and the page reloaded: `dir="rtl"` and `lang="ar"` every time.
* **Sign-in page** (`www/login.py:apply_guest_language`):
  * Opens in the site language (Arabic in Iraq) even when the browser sends `Accept-Language: en`.
  * The **العربية | English** switch (`?_lang=`) is remembered in Frappe's own `preferred_language`
    cookie.

## Translation architecture (load order, last wins)

| Layer | File | Content |
|---|---|---|
| 1. Upstream | `frappe/locale/ar.po`, `erpnext/locale/ar.po` | untouched |
| 2. Terminology layer | `pharmacyos_erp/translations/ar.csv` (generated, ~510 rows) | upstream Arabic rewritten for pharmacy terms |
| 3. Curated layer | `pharmacyos_erp/locale/ar.po` (~710 entries) | PharmacyOS strings and hand-fixed upstream labels |

**Layer 2** is generated by `setup/terminology.py`:

```
bench --site <site> execute pharmacyos_erp.setup.terminology.write_overrides
```

It rewrites term families only inside strings whose *English source* contains the term:

* Batch: دفعة / باتش → **وجبة**. Not applied when the source also mentions Payment, Advance, Instalment
  or Repayment.
* Stock: سهم / أسهم → **مخزون**. Not applied when the source mentions Share.
* Warehouse: مستودع → **مخزن**.
* Customer: عميل → **زبون**.

Re-run it after upgrading ERPNext/Frappe so new upstream strings are covered.

**Layer 3** wins over everything. It holds:

* all PharmacyOS UI strings;
* the requested Iraqi terminology;
* fixes for misleading upstream machine translations seen on daily screens. Examples:
  * *Amount* was كمية, which means "quantity";
  * *Nos* was لا, which means "no";
  * *ID* was هوية شخصية, which means "personal ID card";
  * *Submit* was تسجيل;
  * *Draft* was مشروع;
  * *Due Date* was بسبب تاريخ;
  * *Change Amount* was تغيير المبلغ;
  * *Write Off* was لا تصلح;
  * *Download* and *Upload* were both تحميل.

Context keys (`msgctxt`) are used where one English word needs different Arabic: month names, plural forms,
the grid's row-number header and the greeting comma.

Rules for code:
* No Arabic in business logic.
* Python/Jinja use `_()` and JS uses `__()`.
* Seed data (dosage-form Arabic names, demo data) is data, not logic.

**Translated records.** The *Dosage Form* DocType is a `translated_doctype`, so link fields show
أقراص / كبسول / شراب… to Arabic users. "Patch" is deliberately not translated globally, because Frappe uses
that word for database patches.

**Batch decision.** Iraqi pharmacists call a manufacturing lot a **وجبة**. The upstream دفعة / الدفعات
reads as a *payment* in Arabic, which is dangerous on screens that mix money and stock. PharmacyOS
therefore never shows دفعة / الدفعات / باتش for a stock batch. Payment batches keep دفعة. A test checks
every effective Arabic string to enforce this
(`test_effective_arabic_never_calls_a_stock_batch_a_payment`).

**Brand names are never translated:** PharmacyOS, PharmacyOS ERP and HALF (tested).

## RTL and mixed direction

Frappe flips the layout for RTL languages and serves an `rtlcss`-derived stylesheet. PharmacyOS adds the
following.

### CSS: `public/css/pharmacyos.bundle.css`, section "Arabic-first RTL & bidi"

* **rtlcss pitfall.** rtlcss flips a literal `direction: ltr` to `rtl` and `text-align: right` to
  `left`. Before this pass, that silently broke `.pos-ltr` in Arabic. The LTR rules now take their values
  from custom properties (`--pos-tech-dir`, `--pos-tech-align`), which rtlcss leaves alone.
* **Free-text inputs** use `unicode-bidi: plaintext` with right alignment. An English name typed into an
  Arabic form reads correctly.
* **Technical fields are always LTR and isolated**:
  * barcode, SKU / item code, batch, serial, phone, mobile, e-mail, URL, tax ID;
  * strength (`500 mg`), naming series, supplier delivery note, storefront code;
  * numbers and currency.

  This applies to form inputs, read-only values and grid cells.
* **Arabic line height** is 1.6. Arabic text never gets letter-spacing or upper-casing.

### JS: `public/js/pharmacyos/bidi.js`

* In RTL sessions only, a batched `MutationObserver` marks list, grid, link, title and POS item-name
  values `dir="auto"`. Each value takes its own direction, so "DEMO-AMOX-500" no longer loses its
  first letters and Latin names are truncated at their own end.
* It is presentation only. Values and keystrokes are untouched.

### PharmacyOS pages

* Identifiers render through `<bdi>` / `.pos-ltr` / `ui.ltr()`.
* Amounts sit on their own line instead of inside a sentence, e.g. "Expired batches" with the amount
  below it.
* Percentages are isolated, e.g. `الهامش 39.9%`.
* Directional icons (chevrons, arrows) are mirrored in RTL. Semantic icons (search, check, clock,
  warning) are not.

### Scanner

* Barcode inputs only change rendering direction.
* Verified in the Arabic POS: fast keystrokes to the document are captured by ERPNext's onScan into the
  search field, the medicine is found, and it is added to the cart.

## Typography

* **Arabic:** Tajawal, self-hosted and OFL, limited to Arabic via `unicode-range`. It leads the font
  stack for RTL.
* **Latin:** Inter.
* Mixed medicine names render each script in its own face.

## Formats

* **IQD:**
  * shown as `25,000 د.ع` (Arabic) or `25,000 IQD` (English);
  * the stored symbol `IQD` is translated;
  * an all-zero fraction is hidden by the PharmacyOS formatter;
  * stored precision is unchanged.
* **Numbers:** Latin digits everywhere. Technical IDs are always Latin. Demo data and examples use Latin
  digits. Search folds Arabic-Indic digits (٥٠٠ → 500).
* **Dates:**
  * Storage and APIs stay ISO.
  * PharmacyOS pages and prints show unambiguous dates: `27 تشرين الأول 2026` (Iraqi month names) and
    `27 Oct 2026`.
  * Code: JS `pharmacyos.ui.date`; Jinja `format_display_date`.
  * Pack expiry on prints stays `MM/yyyy`, as printed on medicine packs.
  * Standard ERPNext date inputs use the site's date format (`dd-mm-yyyy`).
* **Day counts** use Arabic plural forms: يوم واحد، يومان، 5 أيام، 45 يوماً.

## Arabic search

* MariaDB's `utf8mb4_unicode_ci` ignores harakat but does **not** equate any of:
  * أ / إ / آ / ا;
  * ى / ي;
  * ة / ه.
* `Item.pharma_search_key` is a hidden custom field, maintained on every save and back-filled by the
  patch. It holds the normalized form (`utils/arabic.py`) of the item code, commercial name, Arabic name,
  generic name, active ingredients (English and Arabic) and barcodes.
* **Normalization rules:**
  * lower-case;
  * harakat and tatweel removed;
  * أإآٱ → ا, ى → ي, ة → ه, ؤ → و, ئ → ي;
  * Arabic-Indic digits → Latin.
* **Where it is used:**
  * Frappe link search (Item `search_fields`);
  * ERPNext POS item search (POS search fields);
  * PharmacyOS Inventory Health;
  * Batches & Expiry;
  * the new `pharmacyos_erp.pharmacy.medicine.search_medicines` API. An exact barcode comes first; the
    API respects the caller's permissions.
* **Remaining limitation:** in ERPNext's own link fields the *query* is not normalized.
  * "ايبوبروفين" finds "إيبوبروفين" through the key.
  * A query typed *with* a hamza only matches names stored with the same hamza.
  * PharmacyOS's own searches normalize both sides.

## Remaining untranslated or upstream surfaces (honest list)

* Upstream help texts not on daily screens. About 26% of upstream ERPNext strings have no Arabic upstream;
  they show in English.
* The POS shows the stock UOM name raw (e.g. "Nos"), because ERPNext does not translate it there. The POS
  page also keeps ERPNext's own shell (dock and title badge).
* Report column headers in some ERPNext reports, the setup wizard, and e-mail templates.
* In the RTL list view, ERPNext's sticky activity column can overlap the last column on narrow widths.
  This is upstream behaviour and the same in English.
* Standard ERPNext forms keep ERPNext layouts. PharmacyOS themes and localizes them; it does not redesign
  them.
